## 한 줄

점검 머신의 컨테이너가 홈랩에 SSH로 접속한다. 홈랩에서는 `gostodian-agent`만 실행된다.  
에이전트는 서비스 정지 → `dnf update` → 재부팅 → 서비스 기동 → 로그 수집을 수행한다.  
점검 머신은 로그를 정규화하고, 규칙으로 판정하고, 민감 정보를 가린 뒤 AI 코멘터리를 붙인다.  
보고서는 S3에 올리고, 알림은 이 프로세스가 Discord로 보낸다.

구현 순서: 접속·에이전트 → 코어 점검 → 정규화·리댁션·보고서·알림

## M0 — 접속 (v0.1.0)

**목표:** 점검 머신에서 홈랩의 `gostodian-agent`만 실행할 수 있다.


| 할 일                                                                                  | README |
| ------------------------------------------------------------------------------------ | ------ |
| 점검 머신에서 컨테이너로 기동 (`docker compose up -d`). 로컬 바이너리는 개발용                               | 5. 실행  |
| YAML 설정. 시크릿 본문은 `secrets/` 파일. 컨테이너에서는 `/run/secrets`. env에는 경로만 둔다                  | 2. 시크릿 |
| SSH ed25519, `knownhosts.New`. 호스트 키 검증을 끄지 않는다                                       | 품질     |
| 홈랩 `authorized_keys`는 `restrict,command="/usr/local/bin/gostodian-agent",from="<점검머신IP>"` | 3. 홈랩  |
| 실행 ID, 구조화 로그, 단계 이력                                                                 | —      |


**완료 기준**

- 점검 머신에서 에이전트 경유로 읽기 점검이 성공한다
- 단위 테스트는 SSH를 흉내 낸다. 실서버는 읽기 전용만

**아직 안 함:** 서비스 정지, dnf, reboot, 로그 수집, 리댁션, AI, S3, Discord

## M1 — 코어 점검 (v0.2.0)

**목표:** README 그림의 원격 작업까지 끝낸다.


| 할 일                                                               | README   |
| ----------------------------------------------------------------- | -------- |
| 설정 파일의 순서대로 서비스 정지·기동. 순서는 service → network → DB. 코드에 하드코딩하지 않는다 | 4. 설정    |
| `dnf update`                                                      | 그림       |
| 재부팅 후 점검 머신이 재접속하고, 서비스 기동                                        | 그림       |
| 로그 수집: dnf, boot, security, fail2ban                              | 4. 설정    |
| 원격 명령은 화이트리스트 테이블로 고정. 문자열로 조립하지 않는다                             | 품질       |
| 단계가 실패하면 파이프라인을 즉시 중단한다                                          | —        |


**완료 기준**

- 한 번의 실행으로 정지 → dnf → reboot → 재접속 → 기동 → 로그 수집이 끝난다
- 실서버 검증은 읽기 점검 다음, 점검 창에서 reboot까지 포함한다

**아직 안 함:** 리댁션, 규칙 판정, AI, S3, Discord

## M2 — 보고·알림 (v1.0.0)

**목표:** 수집한 로그로 보고서를 만들고, 점검 프로세스가 알린다.


| 할 일                                                                 | README |
| ------------------------------------------------------------------- | ------ |
| 로그 정규화. 이상 여부는 규칙으로 판정하고, AI는 코멘터리만 작성한다                            | 그림, 품질 |
| 리댁션: 호스트명, IP, 계정, 토큰. 리댁션 레이어에 골든 테스트를 붙인다                         | 품질     |
| 로그는 신뢰할 수 없는 입력이다. AI에는 구조화된 필드로 넣고 경계를 명시한다                       | 품질     |
| AI 호출이 실패해도 보고서는 만든다. LLM 출력으로는 아무것도 실행하지 않는다                      | 품질     |
| S3 업로드. SSE, PutObject 전용 키. 버킷과 프리픽스는 설정                            | 그림, 4  |
| Discord 웹훅은 이 프로세스가 보낸다. 홈랩에서 도는 메인 봇과 별개다                        | 그림, 서두 |
| 컨테이너가 떠 있는 동안 점검 주기에 맞춰 실행한다                                       | 5. 실행  |


**완료 기준**

- 리댁션된 입력으로 만든 보고서가 설정한 S3 위치에 올라간다
- AI가 실패해도 보고서가 나가고 Discord 알림이 간다
- 알림 주체는 점검 머신이다. 홈랩이 죽어도 알림 프로세스까지 같이 죽지 않는다

이 단계가 끝나면 README에 적힌 점검 흐름이 끝난다.

## 이 로드맵에 넣지 않는 것

- 홈랩 안에서 알림 프로세스를 돌리는 것
- 에이전트 밖의 임의 SSH 명령
- 시크릿 본문을 env에 넣는 것
- 호스트 키 검증을 끄는 것
- LLM 출력을 실행하는 것
- Pipit-hub, 대시보드, 다중 서버
- 점검 실패 자동 롤백
- 전원이나 VPN 원인 세분화, 무응답 전용 상시 모니터
- oCIS / Google Drive를 산출물 저장소로 쓰는 것
